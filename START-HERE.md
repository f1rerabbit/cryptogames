# Запуск проекта с Codex

## Что получится после первых трёх промтов

- монорепозиторий и локальное/серверное dev-окружение;
- responsive игровое лобби в оригинальном дизайне;
- регистрация и роли;
- пользовательский кабинет;
- отдельная админка;
- demo double-entry ledger в TSC;
- безопасная выдача тестовых средств администратором;
- mock game-provider для проверки bet/win/refund;
- бонусы, промокоды и ежедневные награды;
- responsible gaming, audit, базовые risk/KYC-заглушки;
- CI, тесты, Docker Compose и документация.

Это функциональный MVP для разработки и демонстрации, а не готовая к реальным ставкам production-система. Реальный BTC-контур запускается только после Prompt 5, security review и выбора custody.

## Подготовка сервера

Рекомендуется Ubuntu LTS, отдельный непривилегированный пользователь, SSH keys, firewall, Docker Engine + Compose plugin, Git и достаточно диска для images/database. Не запускайте приложение от root. Не открывайте PostgreSQL/Redis в интернет.

```bash
git clone <URL_РЕПОЗИТОРИЯ> platform
cd platform
```

Скопируйте содержимое этого ZIP в корень репозитория так, чтобы `AGENTS.md` находился в корне. Проверьте:

```bash
git status
find prompts docs -maxdepth 2 -type f | sort
```

Авторизуйте Codex обычным поддерживаемым способом вашего клиента. Затем запускайте промты строго по порядку в одном репозитории.

## Порядок

1. Вставьте целиком `prompts/MASTER-01-FOUNDATION.md`.
2. Проверьте отчёт, `git status`, tests и открывающиеся web/admin.
3. После появления существенного UI запустите в новом контексте `prompts/MASTER-CRITIC-LOOP.md`.
4. В новом контексте Codex вставьте `prompts/MASTER-02-PLATFORM-ADMIN-DEMO-MONEY.md`, затем снова `MASTER-CRITIC-LOOP.md`.
5. В новом контексте вставьте `prompts/MASTER-03-BONUSES-COMPLIANCE-HARDENING.md` и проведите итоговый полный `MASTER-CRITIC-LOOP.md`.
6. Не запускайте Prompt 5, пока не выбраны лицензия/custody/KYC/blockchain analytics и critic gate не завершён PASS.

## Почему новый контекст на каждый промт

Код и `docs/PROJECT_STATE.md` сохраняют состояние, а новый контекст уменьшает накопление случайных инструкций. Каждый следующий запуск обязан сначала изучить репозиторий и результаты предыдущего.

Критика особенно полезно запускать в новом контексте: так он меньше склонен принимать собственные решения Builder без повторной проверки.

## Обязательная ручная проверка после каждого промта

- нет незаявленных удалений;
- migrations применяются с нуля;
- demo banner виден;
- TSC невозможно вывести;
- admin grant отражён в ledger/audit;
- обычный пользователь не имеет admin endpoints;
- все quality-gate команды действительно прошли;
- commit отправляется в отдельную ветку/PR, а не сразу в production.

## Ветки

Рекомендуемый порядок: `main` защищён, работа в `feature/master-01`, `feature/master-02`, `feature/master-03`; merge только после CI и ручной проверки. Dev deployment идёт из отдельной ветки/окружения.
